## Claudeの思考

### 要件定義書の全文精読

要件定義書（535 行）を最初に全文 Read した。
設計判断に必要な核心情報として以下をピックアップした：

- 編集機能は 11 モード + ポイント情報 + ウェイポイント = 13 の操作パネルが必要
- Undo/Redo は 50 ステップ
- タイムラインは仮想スクロール必須（10,000 点超対応）
- 標高グラフは On/Off トグル
- 出力は GPX / GeoJSON / KML の 3 形式
- Leaflet + react-leaflet の組み合わせが要件定義書に明記済み

### 技術スタック選定の思考

**ビルドツール**: Vite 一択（ユーザー明示）

**スタイリング**:
- Tailwind CSS を選択。理由: `dark:` バリアントによるダークモード実装が容易、
  かつ Cloudflare Pages の静的配信と相性が良い
- CSS Modules や styled-components も候補だが、ダークモードのトークン管理が複雑になる

**状態管理**:
- Redux Toolkit vs Zustand の比較検討
  - Redux: 厳格な構造、デバッグツールが充実、しかしボイラープレートが多い
  - Zustand: 軽量、immer ミドルウェアでイミュータブル更新を簡潔に書ける
  - **Zustand を選択**。理由: Undo/Redo スタックの実装でスナップショット管理が
    シンプルに書けるため。また React 外（Leaflet イベントハンドラ内）から
    `getState()` で直接参照できる点が Leaflet 統合において有利

**GPX パーサー**:
- `gpxparser` ライブラリ vs 自前実装
  - 外部ライブラリは `extensions` タグを破棄することが多い
  - 「元ファイル形式で保存」には `extensions` 原文の保持が必要
  - **自前実装を選択**。DOMParser ベースで実装し、`_extensions` フィールドに原文を保存

**KML パーサー**:
- `@tmcw/togeojson` を採用（GeoJSON 変換を経由する方式）
- 理由: KML の仕様が複雑で自前パースは工数が高い。GeoJSON 経由でも必要な情報は取得できる

**グラフライブラリ**:
- Chart.js vs Recharts vs Victory
  - Chart.js: 高機能だが React との統合が imperative
  - Recharts: React コンポーネントとして完結、宣言的に書ける
  - **Recharts を選択**

**仮想スクロール**:
- `react-window` vs `@tanstack/react-virtual`
  - react-window は横スクロールの場合に設定が煩雑
  - `@tanstack/react-virtual` は横方向（`horizontal: true`）が標準サポート
  - **@tanstack/react-virtual を選択**

### Undo/Redo 方式の選定

**コマンドパターン**（execute/undo メソッドを持つオブジェクト）vs **スナップショット方式**の比較：

- コマンドパターン: メモリ効率が良い（差分のみ保存）が、編集ロジックごとに undo ロジックを実装する必要があり複雑
- スナップショット: 実装が単純（`structuredClone`）で、50 ステップ × GPX ファイル数 MB → 数百 MB のメモリ使用になりうるが、実用上は許容範囲

**スナップショット方式を選択**。50 ステップ上限でメモリを制御。

### ダークモード実装の思考

3 値トグル（`light / dark / system`）が最もユーザーフレンドリーと判断。
`system` がデフォルトで、`window.matchMedia('(prefers-color-scheme: dark)')` の変化も
リアルタイムに追従させる。

**Leaflet タイルのダークモード問題**:
- Leaflet は `<canvas>` ではなく `<img>` タイルを使うため、CSS `filter` で色反転可能
- `filter: invert(100%) hue-rotate(180deg)` で標準地図は自然な暗色になる
- 航空写真は色反転すると見づらくなるため `noInvert` フラグで除外

### ディレクトリ構成の設計方針

関心の分離を徹底し、以下の原則で分割した：
- `components/` → UI 描画のみ、ロジックは持たない
- `stores/` → グローバル状態のみ（ルート・エディタ・地図・UI）
- `hooks/` → 副作用（ファイル IO・API 呼び出し・キーボードイベント）
- `lib/` → 純粋な関数（パーサー・シリアライザー・編集ロジック・ジオメトリ計算）
- `types/` → 型定義のみ

この構成により、ロジック層（`lib/`）は React に依存しないため、単体テストが容易になる。

### コンポーネント粒度の決定

編集モードが 13 種類あり、それぞれプロパティパネルが異なる。
`PropertiesPanel.tsx` が `mode` に応じて適切なサブコンポーネントに振り分ける構造とした。

`EditMode` は Union 型として定義し、TypeScript の型安全性を活かして
switch 文の網羅性チェックを有効にする。

### ビルド設定（`manualChunks`）の判断

Leaflet + react-leaflet は合計で約 200KB（gzip 後約 60KB）程度あり、
recharts も同程度の重さがある。
`manualChunks` で分割しておくことでブラウザキャッシュを有効活用できる。

### 標高 API のバッチ処理設計

国土地理院の標高 API はレートリミットの公式情報がないが、
ルート作成時のクリックごとにリクエストが走るため、
最大 5 並列・100 件超は 100ms ウェイトを挟む保守的な設計とした。

## 応答の要点

**確定した技術スタック:**
- React 19 + TypeScript 5 + Vite 6 + Tailwind CSS v4
- Zustand + immer（状態管理、4 ストア分離）
- @tanstack/react-virtual（横仮想スクロール）
- Recharts（標高グラフ）
- GPX: 自前パーサー、KML: @tmcw/togeojson、GeoJSON: ネイティブ

**主要な設計決定:**
1. ストアを 4 つに分離（routeStore / editorStore / mapStore / uiStore）
2. Undo/Redo はスナップショット方式（50 ステップ上限）
3. ダークモードは `light / dark / system` の 3 値トグル、航空写真は色反転除外
4. Cloudflare Pages 向けに `manualChunks` でバンドル分割
5. 標高 API は最大 5 並列・バッチ処理
6. ディレクトリを `components / stores / hooks / lib / types` に厳密分離
