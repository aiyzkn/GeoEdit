## ユーザーのプロンプト

```
基本設計書をもとに、実装の準備を行います。
まず、実装する項目を、優先度付きでチェックリストにまとめてください。
まだ実装しないでください。
```

---

## Claudeの思考

### 「まだ実装しないでください」の意図

ユーザーは計画フェーズと実装フェーズを明確に分けたい。
チェックリスト自体を成果物として先に確認・修正できるようにする狙いと判断した。
これはソフトウェア開発の「設計レビュー後に実装着手」という正しいプロセスに従っている。

### 優先度の設定方針

単純な機能重要度ではなく、**開発サイクルで先に必要なものから高優先度**にする。

判断の軸：
1. **他の機能が依存するか**（型定義・ストアはすべての実装の前提）
2. **動作確認に必要か**（地図表示・ファイル読込みがないとデバッグできない）
3. **開発ループを短縮するか**（ファイル出力を先に実装 → 読込み→編集→保存のサイクルを確立）
4. **リスクが高いか**（技術的難易度が高い機能は早めに着手してリスク解消）

優先度の階層：
- **P1**: プロジェクト基盤（設定ファイル・型・ストア）— これがないと何も始まらない
- **P2**: ファイル入力・地図表示 — 目に見える成果ができる
- **P3**: タイムライン・標高グラフ・Undo/Redo・ダークモード — UX 基盤
- **P4**: ファイル出力 — P5 の編集結果を検証するために先に必要
- **P5**: コア編集機能（分割・区間削除・結合・部分編集）
- **P6**: 追加編集機能（間引き・時刻編集・逆順・標高置換など）
- **P7**: タイルレイヤー完全対応（35 種ベースマップ・17 種オーバーレイ）
- **P8**: UI 仕上げ・ヘルプ・レスポンシブ・デプロイ設定

### P4 を P5 より先にした理由

「ファイル出力 → 保存 → GIS ツールで確認」というループが早い段階で回せると、
編集機能の品質確認が格段に楽になる。
また出力は入力に依存するが、編集機能には依存しないので独立して実装できる。

### チェックリストの構造

各優先度を H2 セクション、各タスクを `- [ ]` チェックボックスで記述。
チェックボックスは実装進行中にそのままチェックを入れられる運用を想定した。
