## 1. 概要

ルート作成モード（`mode === 'create'`）で地図をクリックしてポイントを追加する際、クリック地点周辺のタイル画像（ラスタ画像の画素色）をクライアントサイドで解析し、道路中心・交差点重心へポイント座標を補正（スナップ）する。外部サービス（LLM・ルーティングAPI等）は使用せず、すべてブラウザ内で完結する。

### 1.1 確定仕様（ヒアリング結果）

| 項目               | 決定内容                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 対象ベースレイヤー | `gsi-std`（標準）/ `gsi-pale`（淡色）/ `gsi-blank`（白地図）の表示中のみ実行。他レイヤー表示中はクリック座標をそのまま追加 |
| 有効ズーム         | **z ≥ 15**。それ未満はマッチングせずクリック座標を追加                                                                     |
| 一時無効化         | **Ctrl**（macOS は **Cmd**）押下クリックでその1点だけマッチングをスキップ                                                  |
| 恒久無効化         | 作成モードパネルに「マップマッチング」チェックボックス（既定 ON）                                                          |
| 適用範囲           | ①クリックによるポイント追加、②作成中ポイントのドラッグ移動終了時（dragend）の両方                                          |
| 失敗時             | マッチング不能・タイル取得失敗・タイムアウト時はクリック（ドロップ）座標をそのまま採用（サイレントフォールバック）         |

> 白地図（`gsi-blank`）は道路が描画されないため、解析しても道路画素が見つからず実質常にフォールバックとなる（仕様として許容。maxZoom 14 のため z≥15 条件でも実行されない点に注意 — §6.1 参照）。

### 1.2 マッチング動作の分類

| クリック位置     | 動作                                                       |
| ---------------- | ---------------------------------------------------------- |
| 道路上（単路部） | 道路の**中心線上**にスナップ                               |
| 分離帯のある道路 | 分離帯で分かれた**クリックされた側の車道**の中心にスナップ |
| 交差点上         | 交差点領域（道路連結成分）の**重心**にスナップ             |
| 道路外・判定不能 | クリック座標のまま                                         |

道路に被る注記文字・三角点/水準点記号・地下鉄記号等は解析上のノイズとして除去する（§6.3）。

## 2. アーキテクチャ

### 2.1 新規モジュール構成

```
src/lib/mapMatch/
├── index.ts        # 公開API: matchPoint()（前提条件判定→パッチ取得→解析の統括）
├── types.ts        # MatchInput / MatchResult / PixelClass 等の型定義
├── palette.ts      # レイヤー別（std / pale / blank）の色分類テーブル
├── tileSampler.ts  # タイル取得・LRUキャッシュ・クリック周辺パッチ切り出し
└── matcher.ts      # 画素分類・ノイズ除去・道路中心/交差点重心の幾何解析（純粋関数）
```

`matcher.ts` は `ImageData` 相当の生配列を入出力とする純粋関数群とし、Leaflet・DOM に依存させない（ユニットテスト容易性のため）。

### 2.2 既存コードの変更点

| ファイル                                                            | 変更内容                                                                                                                          |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| [MapPane.tsx](../src/components/map/MapPane.tsx)                    | create モードの click ハンドラを非同期化し、`matchPoint()` 経由で `addCreatePoint()` を呼ぶ。クリック順序保証キューを導入（§5.2） |
| [CreateRouteLayer.tsx](../src/components/map/CreateRouteLayer.tsx)  | マーカー `dragend` 時に `matchPoint()` を通してから `moveCreatePointAt()` を呼ぶ                                                  |

| [EditModePanel.tsx](../src/components/properties/EditModePanel.tsx) | create セクションに「マップマッチング」チェックボックスを追加                                                                     |

### 2.3 公開API

```ts
// src/lib/mapMatch/index.ts
export interface MatchResult {
  lat: number
  lng: number
  matched: boolean                       // 補正が行われたか
  kind: 'road' | 'intersection' | 'none' // 判定種別（デバッグ・将来のUI表示用）
}

/**
 * クリック/ドロップ地点をタイル画像解析で道路中心等へ補正する。
 * 前提条件を満たさない場合・解析失敗時は入力座標をそのまま返す（throwしない）。
 */
export async function matchPoint(params: {
  map: L.Map
  latlng: L.LatLng
  baseLayerId: string
  signal?: AbortSignal
}): Promise<MatchResult>
```

## 3. 前提条件判定（ガード）

`matchPoint()` 冒頭で以下をすべて満たす場合のみ解析を実行。1つでも欠ければ即座に `{...入力座標, matched: false, kind: 'none'}` を返す。

1. `editorStore.mapMatchEnabled === true`
2. `baseLayerId ∈ { 'gsi-std', 'gsi-pale', 'gsi-blank' }`
3. `Math.round(map.getZoom()) >= 15`（かつ対象レイヤーの `maxZoom` 以下）
4. 修飾キー（Ctrl / Cmd）が押されていない

修飾キーの取得方法:

- **クリック時**: `L.LeafletMouseEvent.originalEvent` の `ctrlKey || metaKey` を参照（確実）。
- **dragend 時**: Leaflet の dragend イベントには修飾キー情報がないため、`window` の `keydown` / `keyup`（`blur` でリセット）を監視するモジュールレベルの修飾キートラッカー（`modifierState.ts` 相当の小ユーティリティを `mapMatch/` 内に同居）で押下状態を保持し、それを参照する。

## 5. 処理フロー

### 5.1 シーケンス（クリック追加時）

```
map click (create mode)
  │ originalEvent.ctrlKey/metaKey チェック → 押下なら addCreatePoint(生座標) で終了
  ▼
matchPoint()
  │ ガード判定（§3）→ 不成立なら生座標を返す
  ▼
tileSampler: クリック点を中心とする 41×41px パッチを取得
  │ latlng → map.project(latlng, z) でワールドピクセル座標
  │ 必要タイル（最大4枚）を fetch → createImageBitmap → OffscreenCanvas → getImageData
  │ タイルはLRUキャッシュ（後述）。失敗/タイムアウト(1500ms)→ 生座標を返す
  ▼
matcher: 画素分類 → ノイズ除去 → 構造判定 → 補正ピクセル座標を算出（§6）
  ▼
補正ピクセル → map.unproject() → latlng
  ▼
addCreatePoint(lat, lng)
```

### 5.2 クリック順序の保証

タイル取得が非同期のため、連続クリック時に `addCreatePoint()` の実行順がクリック順と入れ替わる可能性がある。MapPane の click ハンドラ内で **Promise 直列キュー**を用いる:

```ts
let queue: Promise<void> = Promise.resolve()
const handleClick = (e: L.LeafletMouseEvent) => {
  const req = { latlng: e.latlng, skip: e.originalEvent.ctrlKey || e.originalEvent.metaKey }
  queue = queue.then(async () => {
    const r = req.skip ? { ...req.latlng, ... } : await matchPoint({ ... })
    useEditorStore.getState().addCreatePoint(r.lat, r.lng)
  })
}
```

- 通常はタイルがブラウザHTTPキャッシュ/LRUキャッシュに乗っており待ちはほぼゼロ
- キュー処理中のマーカークリック削除（`removeCreatePointAt`）と競合しても、`addCreatePoint` は末尾追加のみなので破綻しない

### 5.3 dragend 時

CreateRouteLayer の `dragend` ハンドラで同様に `matchPoint()` を await し、結果で `moveCreatePointAt(i, lat, lng)` を呼ぶ。ドラッグは単発操作のため直列キューは不要。修飾キーは修飾キートラッカー（§3）から取得し、押下中ならマッチングせずドロップ位置をそのまま採用する。

## 6. アルゴリズム詳細

### 6.1 パッチ取得（tileSampler.ts）

- 解析ズーム `z = Math.round(map.getZoom())`。ただし `z > layer.maxZoom` の場合は実行しない（Leaflet が地図の maxZoom をレイヤーに合わせて制限するため通常は発生しないが、防御的にガード）
- クリック点のワールドピクセル座標 `P = map.project(latlng, z)`（GSIタイルは256px、DPRに関わらずタイル画素 = CSSピクセルで一致）
- パッチ: `P` を中心に **半径 R = 20px、(2R+1)² = 41×41px**（要件「周囲20px程度」に対応。`R` は定数 `PATCH_RADIUS` として一元管理）
- パッチが跨るタイル（最大2×2=4枚）を特定し、タイルURL（`tileLayers.ts` の定義から `{z}/{x}/{y}` を展開）を `fetch(url, { signal })` で取得
  - GSIタイルは `Access-Control-Allow-Origin: *` を返すため CORS 読み取り可能（canvas は汚染されない）
  - 表示中タイルと同一URLのためブラウザHTTPキャッシュに命中する想定
- `createImageBitmap()` → `OffscreenCanvas` に必要タイルを配置 → パッチ範囲を `getImageData()` で取得
- **タイルLRUキャッシュ**: `Map<'z/x/y/layerId', ImageData>` 最大16枚。連続クリック・ドラッグでの再取得/再デコードを回避
- タイムアウト: `AbortSignal.timeout(1500)`（呼び出し元 signal と `AbortSignal.any` で合成）。失敗時は上位でフォールバック

> **ダークモードとの関係**: アプリはタイル表示に CSS `invert` フィルタ（`invert-tile` クラス）を使うが、これは表示のみの加工であり、fetch した画像データは常に元の配色。解析は元配色の palette で行うため、ライト/ダークモードの影響を受けない。

### 6.2 画素分類（palette.ts / matcher.ts）

パッチの各画素を以下の4クラスに分類する:

| クラス   | 意味                               | 例（標準地図）                                                            |
| -------- | ---------------------------------- | ------------------------------------------------------------------------- |
| `ROAD`   | 道路の塗り                         | 一般道の白、国道のオレンジ系、高速道路の緑系、都道府県道の黄系            |
| `EDGE`   | 道路縁・輪郭線                     | グレー〜濃グレーの細線                                                    |
| `IGNORE` | 道路に被るが道路構造ではない記号類 | 注記文字（黒〜濃灰）、三角点・水準点記号、地下鉄・鉄道記号、駅名色文字 等 |
| `BG`     | 上記以外（背景・建物・水域など）   | 建物の淡グレー、水域の水色、背景                                          |

- 判定は **レイヤー別 palette テーブル**（`std` / `pale` / `blank` の3セット）との RGB ユークリッド距離 ≤ 許容値（既定 30、色ごとに個別指定可）で行う
- 一般道の塗り（白）と背景（白〜ごく淡いグレー）は近接色のため、**白系は「EDGE に挟まれた白」だけを ROAD とする**のではなく、まず白系をすべて ROAD 候補とし、後段の構造判定（§6.4）で道路形状（EDGE で区切られた帯状/交差点状の領域）でなければフォールバックさせる方針とする（単純・頑健）
- `IGNORE` は「黒・濃灰（注記/記号）」など**明確に道路塗りでも背景でもない色**を割り当て、§6.3 の穴埋め対象とする

> **✅ palette は 2026-07-13 に実タイルのヒストグラム実測で校正済み**（校正タイル座標は `palette.ts` 冒頭コメントに記録）。実測値:
>
> | 要素 | 標準地図 (std) | 淡色地図 (pale) | 分類 |
> |------|--------------|----------------|------|
> | 一般道 | `#ffffff` | `#ffffff` | ROAD（min(R,G,B) ≥ 240 の白系） |
> | 国道 | `#ff7a7a`（許容距離35） | `#ffdc96`（許容距離40） | ROAD |
> | 都道府県道 | `#ffff00` | 白（色分けなし） | ROAD |
> | 高速道路 | `#64c373` | `#78dca0` | ROAD |
> | 道路縁・中間グレー | `#646464`〜`#b1b1b1`（無彩色、輝度95〜190） | 同左 | EDGE |
> | 注記黒・濃色 | 輝度 ≤ 95（`#000000`、駅名緑 `#005a3c` 等） | 同左 | IGNORE |
> | 地下鉄等の青ライン | `#145aff`（高彩度青。水域 `#bed2ff` は明度で除外） | 同左 | IGNORE |
> | 行政界の金色破線 | `#c8a03c` | 同左 | IGNORE |
> | 市街地塗り | `#ff874b`（**国道と近い色のため国道の許容距離は35**） | `#d2d2d2` | BG |
> | 水域 | `#bed2ff` | 同左 | BG |
>
> GSI のタイルデザイン改定時は `palette.ts` のコメントに記録した校正手順（色ヒストグラム実測）を再実施して更新すること。

### 6.3 ノイズ除去（注記・記号の無視）

要件「道路に被っている地名や三角点、水準点、地下鉄などは無視する」への対応:

1. `IGNORE` 画素を対象に**モルフォロジカル・クロージング相当の穴埋め**を行う: `IGNORE` 画素の近傍（半径2px、8近傍拡張）に `ROAD` が一定割合以上あれば `ROAD` に塗り替える
2. 2〜3回反復し、道路上の文字ストローク（幅2〜4px）を吸収する
3. 道路外の注記（背景上の文字）は周囲に `ROAD` がないため `IGNORE` のまま残り、道路と誤認しない

アンチエイリアス縁の中間色は、palette の許容距離と本処理の組み合わせで実用上吸収できる想定。

### 6.4 構造判定と補正座標の算出

入力: 分類済み 41×41 マスク、クリック位置 = パッチ中心 `C`。

**(a) 事前チェック**
- `C` の近傍3px以内に `ROAD` がない → `kind: 'none'`（フォールバック）
- パッチ全体の `ROAD` 率 < 5% → フォールバック

**(b) 連結成分ガード — 境界アーム数**
- クリック点を含む `ROAD` 連結成分（8近傍BFS）を抽出
- 成分がパッチ外周に接する連続 `ROAD` 区間（幅3px以上）を「アーム」として数える
- 外周の道路占有率 > 0.9（広場・パッチ超過道路）→ フォールバック
- **アーム数 ≤ 1 → パッチ内で完結する塊（建物・小広場等）としてフォールバック**

> **v1.1 改訂**: 当初設計の「アーム数 ≥ 3 → 交差点（成分重心へ補正）」は実タイル検証で棄却した。
> 密集市街地では 41px パッチ内に細街路網全体が入り、クリック位置と無関係にアーム数が3以上と
> なって「街路網全体の重心」という無意味な位置へ補正されるため。アーム数は上記ガードにのみ使う。

**(c) 構造判定 — 固定4方向走査**（v1.1 改訂）
1. クリック点 `C` を通る**固定4方向**（水平・垂直・両対角）の走査線上を `t = −R … +R`（1px刻み、最近傍サンプリング）で分類値を読む
   - 当初設計は成分モーメントの主方向に垂直な1本のみを走査していたが、対称な交差点では
     モーメントが縮退して方向が不定になるため固定4方向に変更した。斜め方向の最大誤差22.5°は、
     「直線道路を横切る任意の弦の中点は中心線上に乗る」性質により補正精度へほぼ影響しない
2. 各走査線で連続する `ROAD` を「run」として抽出し、`t = 0` を含む（または距離 ≤ 6px の最寄りの）run を選ぶ
   - 1pxの BG/IGNORE ギャップ（アンチエイリアス起因）は連結して1つの run とみなす
   - **EDGE（道路縁）は幅1pxでも必ず区切り**（白い歩道・街区への誤連結防止）
   - **2px以上のギャップ（分離帯等）は run の区切り** → 分離帯対応
3. 判定:
   - run が走査線の端に達する方向（＝道路が途切れず境界が見えない）が **2方向以上 → 交差点**。
     `ROAD` マスクの**距離変換（3-4チャンファー）がクリック近傍（チェビシェフ距離12以内）で
     最大となる点**（＝交差点領域で最も開けた中心）を補正座標とする
   - それ以外で、両端の見える run が存在 → **単路部**。**最も幅の狭い run**（＝道路をほぼ垂直に
     横切る断面）の**中点**を補正座標とする
   - どちらも該当しない（run なし等）→ フォールバック

**(d) 座標確定**
- 補正ピクセル座標 → ワールドピクセル → `map.unproject(_, z)` → latlng
- 妥当性ガード: 変位が R px を超える結果は棄却してフォールバック（アルゴリズム上は発生しないが防御的に）

### 6.5 分離帯の扱い（要件との対応）

分離帯（中央分離帯が EDGE / BG 色で描かれる）は (c)-2 の run 分割により自動的に「2本の道路」として扱われ、クリックされた側の run 中点にスナップされる。専用の分離帯検出ロジックは持たない（シンプルさ優先）。

## 7. パフォーマンス

| 処理                 | 見積り                                                                            |
| -------------------- | --------------------------------------------------------------------------------- |
| タイル fetch         | 通常0ms台（HTTPキャッシュ/LRU命中）、初回のみネットワーク（〜数百ms、上限1500ms） |
| ImageBitmap デコード | 1〜5ms/枚（LRUで再利用）                                                          |
| 画素分類＋構造解析   | 41×41 = 1,681画素、< 1ms                                                          |

メインスレッドで十分軽量なため **Web Worker は使用しない**。OffscreenCanvas はメインスレッドから直接使用する（未対応環境では通常の `<canvas>` にフォールバック — 対象ブラウザ的にほぼ不要だが1行で書ける）。

## 8. テスト計画

### 8.1 ユニットテスト（matcher.ts / palette.ts — 純粋関数）

`tests/*.test.ts`（`npm test` = `node --test`。Node の型ストリッピングで TypeScript を直接実行するためビルド・追加依存なし）。合成パッチ（プログラム生成した41×41配列）で以下を検証（**全19件 PASS**）:

1. 水平/垂直/斜め45°の帯状道路 → 中心線にスナップ
2. 分離帯付き道路（2本の帯＋中央ギャップ）→ クリック側の帯中心にスナップ、分離帯上クリック → 近い側へ
3. 1px幅の道路縁（EDGE）でも run が区切られる（白い歩道への誤連結防止）
4. 十字路 → 交差点領域の中心 / T字路 → 合流部付近
5. 市街地の細街路網 → クリック近傍の街路中心（網全体の重心へ飛ばない。v1.1 改訂の回帰テスト）

## 9. 制限事項・既知のリスク

1. **palette は地理院タイルのデザイン改定に追従が必要**（校正タイル座標をコメントに残し再校正可能にする）
2. **大型交差点**: パッチ（41×41px）が交差点全体を覆えない場合、補正点（距離変換の最大点、探索半径12px）が真の交差点中心からずれる。要件の「周囲20px程度」を優先し許容する
3. **高架・立体交差・並走鉄道**: 平面画像解析のため、重なった道路の区別はできない。誤スナップ時は Ctrl+クリックまたはドラッグ修正で回避
4. **白い広場・駐車場**: 一般道と同じ白系のため ROAD 候補になり得るが、帯状構造チェック（run 両端到達でフォールバック）で大半は棄却される
5. **黒い太線輪郭の大型建物（例: 東京証券取引所ビル）の内部**: 建物内部の白が道路色と同一のため、輪郭の黒（IGNORE）が注記穴埋めで吸収され、偽の道路/交差点判定になることがある（実タイル検証で確認）。補正量はパッチ半径以内で建物内に留まるため実害は小さく、Ctrl+クリックで回避可能。色情報のみでは白い建物内部と道路を区別できないため制限として許容する
6. **ベクトルタイル（gsi-vector）は対象外**（ラスタ画像が存在しないため。将来対応するならベクトルデータの道路ジオメトリを直接使う別方式が適切）
7. dragend のマッチング中（最大1.5秒）に同一マーカーを再ドラッグした場合の競合は、直後の `moveCreatePointAt` が後勝ちになるだけで破綻はしない
