外部ライブラリ（gpxparser）に依存せず、**自前の XML パーサー**を実装する。  
理由: GPX の extensions タグを保持した「元ファイル形式で保存」に対応するため、
外部ライブラリが破棄する情報を保持する必要がある。

## 4. 内部データモデル

ファイル形式に依存しない共通データ構造として定義する。

```typescript
// types/route.ts

export interface TrackPoint {
  lat: number;
  lng: number;
  ele?: number;               // 標高 (m)
  time?: Date;                // UTC
  waypoint?: WaypointData;    // このポイントに紐づくウェイポイント属性（name/desc/sym）
  _extensions?: string;       // GPX の <extensions> タグ原文（元形式保存用）
}

export interface WaypointData {
  name?: string;   // <name>
  cmt?: string;    // <cmt>
  desc?: string;   // <desc>
  sym?: string;    // <sym>
}

export interface Track {
  name?: string;
  number?: number;
  points: TrackPoint[];
}

// GPX (topografix.com/gpx.asp) の3要素タイプ。通常の作業軌跡は 'track' として記録される。
export type RouteKind = 'waypoint' | 'route' | 'track';

// 単独ウェイポイント（<wpt> 要素）。TrackPoint とは異なり座標そのものを保持する。
export interface Waypoint extends WaypointData {
  lat: number;
  lng: number;
  ele?: number;
  time?: Date;
}

export interface RouteData {
  id: string;                   // ランダム UUID（内部管理用）
  name: string;                 // ルート名（= ファイルベース名 / <name>タグ）
  sourceFormat: 'gpx' | 'kml' | 'geojson';
  sourceFileName: string;       // 元ファイル名（出力デフォルト名の生成に使用）
  kind: RouteKind;              // このルートが表す GPX 要素種別（4.1 参照）
  tracks: Track[];               // kind が 'route' | 'track' のときの本体データ
  standaloneWaypoints: Waypoint[]; // kind が 'waypoint' のときの本体データ、または trk/rte に付随する独立ウェイポイント
  color?: string;               // 表示色（カスタマイズ時）
}
```

### 4.1 GPX 要素種別（`RouteKind`）と相互変換

要件定義書 4.5 に基づき、ルートは `kind` フィールドで 3 種別のいずれかを表す。データは以下のように格納する：

- `kind === 'track' | 'route'`: 順序付きの経路データを `tracks[].points` に格納する（`<trk>` と `<rte>` は同一の「順序付きpath」として同じ配列構造を共有し、`kind` によって GPX 出力時のタグのみを切り替える）
- `kind === 'waypoint'`: 順序を持たない単独ポイント群を `standaloneWaypoints` に格納する。`tracks` は空配列になる

変換ロジックは `lib/editors/routeEditors.ts` の `convertRouteKind(route, kind)` に集約する（純粋関数、`RouteData` を受け取り新しい `RouteData` を返す）：

```typescript
// track <-> route: データはそのまま、kind タグのみ変更
// -> waypoint: tracks[].points を全て standaloneWaypoints へ平坦化（既存分と統合）、tracks を空に
// waypoint -> track/route: standaloneWaypoints を1本の新規トラックに変換、standaloneWaypoints を空に
```

`useFileLoader.ts` はファイルパース直後にこの関数を呼び、`uiStore.openAsKind`（ツールバーの「開く形式」セレクタで選択された値）を適用する。パーサー側は GPX の実際の要素構成から `kind` の初期値を自動判定する（`<trk>` があれば `'track'`、無く `<rte>` があれば `'route'`、両方無ければ `'waypoint'`）が、`openAsKind` が指定されていれば `convertRouteKind` によって上書きされる。

`RouteList.tsx` の各行にある種別アイコンボタンをクリックすると `convertRouteKind` が呼ばれ、Undo 対象として記録される（トラック→ルート→ウェイポイント→トラック…の順で循環）。

地図表示（`RoutePolyline.tsx`）は `kind` に応じて描画方法を変える：

| kind | 描画 |
|------|------|
| `track` | 実線ポリライン（既定） |
| `route` | 破線ポリライン（`dashArray: '8 6'`） |
| `waypoint` | 個別の `L.CircleMarker`（接続線なし）、`standaloneWaypoints` から描画 |

### 4.2 ルートの色管理

`RouteData.color` が設定されていればその色を使い、未設定の場合は読み込み順に 8 色パレットから循環割当する。  
パレット定義とヘルパー関数は `src/lib/colors.ts` に集約し、`MapPane` と `RouteList` で共有する。

```typescript
// src/lib/colors.ts
export const ROUTE_COLORS = [
  '#3b82f6', '#ef4444', '#22c55e', '#f59e0b',
  '#8b5cf6', '#ec4899', '#06b6d4', '#f97316',
]

export function routeColor(routeColor: string | undefined, idx: number): string {
  return routeColor ?? ROUTE_COLORS[idx % ROUTE_COLORS.length]
}
```

カラーピッカー（右サイドバーの色スウォッチ）で変更した色は `updateRoute()` で即座に `RouteData.color` へ書き込まれ、`RoutePolyline` の `useEffect` が再実行されてポリライン色が更新される。

## 5. 状態管理設計

Zustand を使用し、関心ごとに 4 つのストアに分離する。  
各ストアは immer ミドルウェアを適用し、ミュータブルな書き方でイミュータブル更新を行う。

### 5.1 routeStore

読み込み済みルートと選択状態を管理する。実装（`src/stores/routeStore.ts`）は以下の通り。
選択状態は「選択中ルートID」「選択中トラックインデックス」「選択中ポイントインデックス」の
3つのスカラ値に分割して保持し、複合オブジェクトは使わない（選択トラック・ポイントは
選択中ルートに暗黙的に従属する）。

```typescript
interface RouteStore {
  routes: RouteData[];                 // 読込み済みルート一覧
  selectedRouteId: string | null;      // 編集対象ルートの ID
  selectedTrackIndex: number;          // 選択中ルート内のトラックインデックス
  selectedPointIndex: number | null;   // 選択中トラック内のポイントインデックス
  hoveredPointIndex: number | null;    // ホバー中ポイント（タイムライン↔地図の一時ハイライト用）

  // Actions
  addRoute: (route: RouteData) => void;
  removeRoute: (id: string) => void;
  // 更新は immer ミューテータコールバック方式（新しい値を渡すのではなく draft を書き換える）
  updateRoute: (id: string, updater: (route: RouteData) => void) => void;
  setRoutes: (routes: RouteData[]) => void;   // Undo/Redo でスナップショットを一括復元する際に使用
  selectRoute: (id: string | null) => void;   // 選択時に selectedTrackIndex=0 / selectedPointIndex=null にリセット
  selectTrack: (trackIndex: number) => void;  // 選択時に selectedPointIndex=null にリセット
  selectPoint: (index: number | null) => void;
  hoverPoint: (index: number | null) => void;
}
```

> **注記**: ルートの表示色は専用アクションを設けず `updateRoute(id, (r) => { r.color = color })` で書き込む（4.2 と整合）。旧設計にあった `activeRouteId` / 複合オブジェクト型 `selectedPointIndex` / `setActiveRoute` / `setSelectedPoint` / `setRouteColor` / 値渡しの `updateRoute` は上記の実装に置き換えられている。

### 5.2 editorStore

編集モードと Undo/Redo スタックを管理する。

```typescript
type EditMode =
  | 'none' | 'create' | 'partialEdit' | 'split'
  | 'deleteRange' | 'merge' | 'thinOut' | 'timeEdit'
  | 'rename' | 'waypoint' | 'reverse' | 'elevReplace'
  | 'pointInfo' | 'export';

interface UndoEntry {
  description: string;
  snapshot: RouteData[];   // 編集前の routes 深コピー
}

// 部分編集モード（6.2）の作業コピー。確定まで元のトラックには反映しない。
interface PartialEditState {
  routeId: string;
  trackIndex: number;
  startIndex: number;       // 元トラック内での編集範囲開始インデックス（splice の目印）
  originalLength: number;   // 確定時に置換する元ポイント数
  points: TrackPoint[];     // 編集用の作業コピー（最大601点、ドラッグ・追加・削除の対象）
}

interface EditorStore {
  mode: EditMode;
  undoStack: UndoEntry[];   // 最大 50 件
  redoStack: UndoEntry[];
  selection: SelectionRange | null;              // 部分削除（deleteRange）用の範囲選択
  isBusy: boolean;                               // 標高API取得中などの処理中フラグ
  draft: Draft;                                  // ルート作成モードの下書き（通過点 anchors と区間 legs。経路探索詳細設計書 §8.1）
  draftPast: Draft[]; draftFuture: Draft[];      // 下書きの取り消し・やり直しの履歴（上限 100。下記参照）
  routingSettings: RoutingSettings;              // 経路探索の設定（利用者ごと。localStorage `geoedit-routing`。同 §11）
  routingProgress: { done: number; total: number } | null; // 道路データの取得の進み具合
  mergeTargetIds: [string | null, string | null]; // 結合モードで選択中の2ルートID
  partialEdit: PartialEditState | null;           // 部分編集モードの作業コピー（null = 非編集中）

  // Actions（モード切替時、対象外の一時データは自動クリアされる）
  setMode: (mode: EditMode) => void;
  pushUndo: (description: string, snapshot: RouteData[]) => void;
  // undo/redo は「Undo/Redo 実行直前の現在 routes」を引数で受け取り、反対側スタックへ退避する
  // 標準的な2スタック方式（下記「Undo/Redo 設計」参照）
  undo: (currentRoutes: RouteData[]) => UndoEntry | null;
  redo: (currentRoutes: RouteData[]) => UndoEntry | null;
  setBusy: (busy: boolean) => void;
  toggleMergeTarget: (routeId: string) => void;
  startPartialEdit: (state: PartialEditState) => void;
  movePartialEditPoint: (index: number, lat: number, lng: number) => void;
  removePartialEditPointAt: (index: number) => void;   // 始点・終点は削除不可
  insertPartialEditPointAt: (index: number, point: TrackPoint) => void;
  setPartialEditPointEle: (index: number, ele: number) => void;
  clearPartialEdit: () => void;
  // ほか: setSelection / toggleDeleteRangeMarker /
  //       addCreatePoint / removeCreatePointAt / removeLastCreatePoint /
  //       redoCreatePoint / clearCreatePoints / moveCreatePointAt
}
```

`setMode()` はモード遷移時に他モードの一時データを破棄する（例: `merge` 以外へ移ると `mergeTargetIds` を `[null, null]` に、`partialEdit` 以外へ移ると `partialEdit` を `null` に戻す）。これにより「確定前にモードを変更すると作業内容はリセットされる」（要件定義書 6 章共通仕様）を保証する。

**ルート作成モードの下書きの Undo/Redo（`draft` / `draftPast` / `draftFuture`）**: ルート作成中の下書きは、確定済みルート（`routeStore.routes`）を対象とする通常の Undo/Redo スタックの対象外である。`create` モード中の Ctrl+Z / Ctrl+Y は `draftController.undo()` / `redo()` を優先的に呼び、操作（通過点の追加・移動・差し込み・削除・引き直し）ごとの下書きのスナップショットを戻す（区間の線ごと戻るので、探索はやり直さない。探索中だった区間だけ頼み直す）。履歴が空なら通常のルートレベル Undo/Redo にフォールバックする。2026-11 に、末尾の 1 点だけを退避する旧方式（`createPoints` / `createRedoPoints`）から置き換えた（経路探索詳細設計書 §8.3・§8.4）。

## 7. ダークモード設計

### 7.1 切り替え方式

| モード | 動作 |
|--------|------|
| `system`（デフォルト） | `prefers-color-scheme: dark` に従って自動切替 |
| `light` | 常にライトモード |
| `dark` | 常にダークモード |

設定値は `localStorage` に永続化（キー: `gpx-editor-theme`。5.4 と一致）。

### 7.2 適用方法

`App.tsx` で `resolvedDark` が `true` の場合に `<html>` 要素へ `dark` クラスを付与する。  
Tailwind CSS の `dark:` バリアントで各コンポーネントの色を定義する。

```typescript
// hooks/useDarkMode.ts
useEffect(() => {
  const mql = window.matchMedia('(prefers-color-scheme: dark)');
  const update = () => {
    const resolved = colorScheme === 'dark'
      || (colorScheme === 'system' && mql.matches);
    setResolvedDark(resolved);
    document.documentElement.classList.toggle('dark', resolved);
  };
  update();
  mql.addEventListener('change', update);
  return () => mql.removeEventListener('change', update);
}, [colorScheme]);
```

### 7.3 ダークモード切替ボタン

ツールバー右側に 3 値トグル（☀️ライト / 🌙ダーク / 💻システム）を配置。  
クリックで `light → dark → system → light …` とサイクル。

### 7.4 地図（Leaflet タイル）のダークモード対応

ラスタータイル全般（標準地図・OSM 等）にはダークモード時に CSS フィルタを適用する。  
航空写真タイル（seamlessphoto / Esri / Google 衛星）は色反転しない（`noInvert: true` フラグで管理）。

```css
/* dark モード時にタイルレイヤーに適用 */
.leaflet-dark-tile .leaflet-tile {
  filter: invert(100%) hue-rotate(180deg) brightness(95%) contrast(90%);
}
```

各タイルレイヤーの定義に `noInvert` フラグを持たせ、レイヤー切り替え時に CSS クラスを付け外しする。

## 8. Leaflet 統合設計

### 8.1 Leaflet の直接操作方針

- `MapPane.tsx` で `useRef<HTMLDivElement>` + `useEffect` を使って `L.map()` を直接初期化
- コンポーネントアンマウント時に `map.remove()` でクリーンアップ
- Leaflet のイベントハンドラ内で Zustand ストアを `store.getState()` で参照し、React の stale closure 問題を回避する
- `RoutePolyline.tsx` はレンダリング上は `null` を返し、`useEffect` 内でポリライン・マーカーを追加／更新／削除する純粋な副作用コンポーネントとして設計する

### 8.2 マーカーのパフォーマンス対策

部分編集時（最大 601 個）の編集マーカーは `L.DivIcon` を使用する。  
ポイント情報モードやウェイポイントマーカーは通常の `L.CircleMarker` を使用する。

**選択中ポイントのドラッグ編集**: `L.CircleMarker` は `draggable` オプションを持たないため、選択中ポイントのハイライト用マーカーのみ `L.Marker` + `L.divIcon()`（円形の `<div>` を丸ごとHTML文字列で指定）に置き換え、`draggable: true` を指定する。`dragend` イベントで新しい緯度経度を確定し、Undo スナップショットを保存してから `routeStore.updateRoute()` を呼ぶ（ドラッグ中の `drag` イベントでは更新しない — 連続的な Undo 積み上げやポリラインとの不整合を避けるため、確定は `dragend` の一度だけ）。

### 8.3 タイルレイヤー定義（types/tile.ts・lib/tileLayers.ts）

```typescript
// types/tile.ts（実装時の実際のフィールド名。v1.0時点の草案とは name→label, isVector→type 等が異なる）
export type TileType = 'raster' | 'vector';
```

**重ね合わせオーバーレイの描画とZ順（2026-07-02 実装・修正）**: `MapPane.tsx` は `mapStore.activeOverlays`（`{id, opacity}[]`）を購読し、有効なオーバーレイごとに `L.tileLayer()` を生成して地図に追加・削除・`setOpacity()` 更新する（`overlayLayersRef` で `id → L.TileLayer` を管理する差分更新）。オーバーレイタイルは `map.createPane('rasterOverlay')` で作成した専用ペイン（z-index: 350）に描画する。これはLeaflet標準の `tilePane`（z-index: 200、ベースマップ）より上、`overlayPane`（z-index: 400、ルートのポリライン・マーカー等）より下に位置し、「オーバーレイを重ねるとベースマップしか見えない」「オーバーレイがルート表示を隠してしまう」の両方を防ぐ。なお `L.Map#createPane(name)` は内部でペイン名から文字列 `"Pane"` を除去してCSSクラス名を組み立てる（例: `'rasterOverlayPane'` → `leaflet-rasterOverlay-pane`）ため、紛らわしさを避けて末尾に `"Pane"` を含まないペイン名 `'rasterOverlay'` を使っている。ダークモードの色反転CSS（`.invert-tile`）もこのペインに対応させている。

**透明度プリセットの統合（2026-07-02）**: 要件定義書5.2は当初「OSM 20%」「OSM 40%」のように透明度ごとに個別レイヤーとして定義していたが、`LayerPanel.tsx` に0〜100%（5%刻み）のスライダーを実装済みであるため、プリセット別の重複エントリは撤廃し1タイルソース1エントリに統合した（初期透明度は0.4）。`gsj-geology-ov-20`/`gsj-geology-ov-40` は専門レイヤー群に既存の `gsj-geology-ov`（地質図（重ね）、同一URL）と完全重複していたため、統合のタイミングで削除し1件に一本化した。

### 8.4 ベクトルタイル統合（MapLibre GL）

`MapPane.tsx` にベースレイヤー生成の共通ヘルパー `createBaseLayer(layerDef)` を実装し、初期化時・レイヤー切替時の両方から呼び出す:

```typescript
function createBaseLayer(layerDef: TileLayerDef): L.Layer {
  if (layerDef.type === 'vector') {
    return L.maplibreGL({
      style: layerDef.style!,
      attributionControl: { customAttribution: layerDef.attribution },
    })
  }
  return L.tileLayer(layerDef.url!, { attribution: layerDef.attribution, maxZoom: layerDef.maxZoom ?? 18, className: layerDef.noInvert ? '' : 'invert-tile' })
}
```

- `L.maplibreGL` は `@maplibre/maplibre-gl-leaflet`（`import '@maplibre/maplibre-gl-leaflet'` の副作用importで `L` 名前空間に追加される）が提供する `L.Layer` 派生クラス
- ラスターの `L.TileLayer` は `bringToBack()` を持つがベクターの `MaplibreGL` レイヤーは持たないため、レイヤー切替時は `typeof (tile as L.TileLayer).bringToBack === 'function'` でガードしてから呼び出す
- **既知の制約**: `@maplibre/maplibre-gl-leaflet` は内部でMapLibreの表示ズームとLeafletのズームを同期するが、ベクトルレイヤーへの切替時に表示ズームがわずかに変化することがある（プラグイン自身のREADMEが記す既知の制限で、回転非対応・パフォーマンス低下と並ぶ制約の一つ）。ラスターへ戻すと元のズームに復帰することを確認済み
- **データソースとスタイルの自作**（`lib/gsiVectorStyle.ts`）: 国土地理院公式の `style.json`（`https://maps.gsi.go.jp/vector/data/*.json`）は version/sources/layers を持つ完全なMapLibreスタイルではなく国土地理院独自形式（実際の描画には専用の合成JSが必要）と判明したため、同じベクトルタイルデータソース（`experimental_bvmap`、`{z}/{x}/{y}.pbf`）を対象に、`@mapbox/vector-tile` + `pbf` でタイルを直接デコードして実在する source-layer 名（building/label/symbol/elevation/road/railway/structurea/river/waterarea）を特定し、道路・建物・水域・鉄道・地名ラベル（`label`レイヤーの`knj`プロパティ）の基本レイヤーのみを自前定義した `GSI_VECTOR_STYLE`（`StyleSpecification`）を実装した

### 8.5 地名検索・ジャンプ（PlaceSearch.tsx）

`MapPane.tsx` 内に地図左上のオーバーレイとして配置する独立コンポーネント。`lib/geocodeApi.ts` の `searchPlace(query)` が国土地理院ジオコーディングAPI（`https://msearch.gsi.go.jp/address-search/AddressSearch?q=...`）を呼び出し、`{ title, lat, lng }[]` を返す。検索結果一覧から1件クリックすると `map.setView([lat, lng], 15)` で地図をジャンプする。

**Leaflet標準ズームコントロールとの重なり対策（2026-07-02）**: 検索ボックスもLeafletのデフォルトズームコントロール（`zoomControl: true`）も、ともに地図左上（`.leaflet-top.leaflet-left`）に配置されるため重なって隠れてしまう問題があった。`index.css` に `.leaflet-top.leaflet-left .leaflet-control-zoom { margin-top: 52px; }` を追加し、ズームボタンを検索ボックスの下に少しずらすことで解消した。

### 9.2 GPX パーサー仕様（lib/parsers/gpxParser.ts）

- DOMParser を使用して XMLを解析。`<parsererror>` 要素が生成された場合は不正XMLとして例外を送出し、`useFileLoader` がエラートーストを表示する（基本設計書16.2）
- `<trkseg>` 1つを Track 1件として `tracks` に格納する（1つの `<trk>` に複数 `<trkseg>` がある場合、それぞれ別 Track になる）。**既知の制約**: この方式のため元の `<trk>`/`<trkseg>` の入れ子構造は保存されず、「元ファイル形式で保存」でも各 Track が個別の `<trk>` として出力される（セグメント境界を編集単位として扱う設計。2026-07-03 に設計を実装に合わせて更新）
- `<trkpt>` の子要素: `<ele>`, `<time>`, `<extensions>` を保持
- `<rte>` → `<trk>` と同じ Track 構造として `tracks` に格納（`<rtept>` は `<trkpt>` と同じ座標・付加情報を持つため共通のポイントパーサーを再利用）
- `<wpt>` → `standaloneWaypoints`（`lat`/`lon` 属性・`<ele>`/`<time>`/`<name>`/`<desc>`/`<sym>` を保持する `Waypoint` として格納。座標を保持しない旧実装のバグを修正済み）
- `<extensions>` の XML 文字列を `_extensions` に保存（元ファイル形式での出力に使用）
- `kind` の自動判定: `<trk>` が1つ以上あれば `'track'`、無く `<rte>` が1つ以上あれば `'route'`、どちらも無ければ（`<wpt>` のみ）`'waypoint'`（4.1 参照）

### 9.3 出力フロー

```
ExportProps.tsx（フォーム）
  └─ useFileExporter.ts
       ├─ 対象ルート・出力形式・オプションを受け取る
       ├─ gpxSerializer / kmlSerializer / geojsonSerializer で文字列生成
       ├─ Blob → Object URL → <a> クリック でダウンロード
       └─ ファイル名: `{sourceFileName}_ed.{ext}`（変更可能）
```

**ファイル名の不正文字置換（2026-07-02 修正）**: `useFileExporter.ts` の `exportRoute()` はファイル名に含まれる、OS のファイルシステムで使用できない文字（`< > : " / \ | ? *` および制御文字）を `_` に置換してからダウンロードする。従来は `.replace(/[^\w\-. ]/g, '_')` という正規表現を使っていたが、`\w` は ASCII の英数字とアンダースコアにしかマッチせず日本語等の非ASCII文字を「不正文字」とみなしてしまうため、日本語のルート名・ファイル名がすべてアンダースコアに置換されるバグがあった。実際に禁止すべき文字だけを列挙する正規表現（`/[<>:"/\\|?*\x00-\x1f]/g`）に修正し、日本語を含む任意の言語のファイル名がそのままダウンロードされるようにした。

**エクスポートダイアログの形式ボタン順序（2026-07-02）**: `ExportDialog.tsx` の形式選択ボタンは GeoJSON → GPX → KML の順で表示する。

### 9.4 GPX シリアライザ仕様

| オプション | 動作 |
|-----------|------|
| 元ファイル形式 + wpt 有 | trkpt の `_extensions` を復元、wpt タグを出力 |
| 元ファイル形式 + wpt 無 | trkpt の `_extensions` を復元、wpt タグを省略 |
| 最小サイズ + wpt 有 | trkpt は lat/lon/ele/time のみ、wpt タグを出力 |
| 最小サイズ + wpt 無 | trkpt は lat/lon/ele/time のみ、wpt タグを省略 |

**`kind` による出力タグの切り替え**（`gpxSerializer.ts`）:

- `kind === 'track'`: `tracks[]` を `<trk><trkseg><trkpt>...` として出力（既定）
- `kind === 'route'`: `tracks[]` を `<rte><rtept>...` として出力（`<trkseg>` に相当するラップ要素は無い）
- `kind === 'waypoint'`: `tracks` は空のため出力対象になるのは `standaloneWaypoints` のみ。この場合、`standaloneWaypoints` がルートの本体データそのものであるため「wpt 無」オプションを選んでいても常に出力する（`includeWpt` を強制的に true にする）
- `trkptTag` / `rteptTag` / `wptTag` は共通の `pointTag(tagName, pt, mode)` ヘルパーを介して実装し、タグ名以外の出力ロジック（ele/time/name/desc/sym/extensions・minimal モードでの省略）を重複させない

**GeoJSON / KML シリアライザの対応**:

- `geojsonSerializer.ts`: `tracks[]` を LineString Feature として出力するのに加え、`standaloneWaypoints` を Point Feature として出力する（従来は未出力だった欠落を修正）
- `kmlSerializer.ts`: `standaloneWaypoints` の Placemark に `<Point><coordinates>` を追加（従来は座標を持たない `Waypoint` 型だったため座標なしの Placemark になっていたバグを修正）

## 10. Undo/Redo 設計

### 10.1 方式

スナップショット方式を採用する。  
各確定操作の直前に `routes` 配列（RouteData[]）を深コピーして undoStack に積む。  
メモリ効率よりも実装シンプルさを優先する（GPX ファイルサイズは通常数MB 以下）。

### 10.2 フロー

```
編集操作の確定直前:
  1. editorStore.pushUndo('操作名', structuredClone(routeStore.routes))
  2. routeStore.updateRoute(...) で新しい routes に更新

Undo:
  1. editorStore.undo(現在のroutes) が undoStack から pop し、旧 routes スナップショットを返す
     と同時に、引数で受け取った「Undo実行直前の現在routes」を redoStack へ push する
  2. 呼び出し側（AppHeader / useKeyboard）が routeStore を旧スナップショットで上書き

Redo:
  1. editorStore.redo(現在のroutes) が redoStack から pop し、次の routes スナップショットを返す
     と同時に、引数で受け取った現在routesを undoStack へ push する
  2. 呼び出し側が routeStore を上書き
```

> **注記（2026-07-03 修正）**: 以前の実装は `undo()` が pop した「編集前スナップショット」をそのまま redoStack へ積んでいたため、Redo を押しても編集前状態が再セットされるだけで機能していなかった。本設計10.2の通り「Undo/Redo 実行直前の現在 routes を反対側スタックへ退避する」2スタック方式に実装を修正した（`undo`/`redo` が現在 routes を引数で受け取るようシグネチャ変更）。

### 10.3 Undo 対象外の操作

- ルート削除（削除は Undo 対象とし、誤操作を保護する）
- ウェイポイントの追加・削除（即時反映だが Undo 対象とする）
- タイルレイヤー切り替え
- ペインサイズ変更
- ダークモード切り替え

各ポイント間のセグメントに時間を配分するため、標高差と水平距離から勾配を求め、勾配別の
**絶対速度（km/h）テーブル**を線形補間して区間所要時間を算出する（実装は「基準速度×速度比」方式ではなく
勾配→絶対速度の直接テーブル。2026-07-03 の監査で設計を実装に合わせて更新）。

```
勾配(%) = (標高差 / 水平距離) × 100
速度(km/h) = interpolateSpeed(勾配)   // 下表を線形補間、範囲外は端値でクランプ
セグメント所要時間 = 水平距離 / (速度 × 1000 / 3600)
```

速度テーブル（`SPEED_TABLE`、勾配% → 速度 km/h。テーブル外は端値）:

| 勾配 (%) | 速度 (km/h) |
|---------|-------------|
| -30 | 1.5 |
| -20 | 2.0 |
| -10 | 3.5 |
| 0（平地） | 4.0 |
| 10 | 3.0 |
| 20 | 2.2 |
| 30 | 1.5 |

- 開始・終了日時の両方が指定された場合（`redistributeTimeWithRange`）は、上記で相対配分した後に合計時間が指定範囲に一致するよう各区間を比例スケーリングする。
- 部分編集での挿入ポイントの時刻補間（`interpolatePointTime`）も、この速度テーブルで前後2区間の所要時間比を求めて配分する（標高差・距離の両方を反映、要件定義書6.2。挿入直後は標高未取得のため前後標高から距離比で推定）。

### 14.3 結合アルゴリズム（routeEditors.ts）

`mergeRoutesUnified(tracksA, tracksB)` / `mergeRoutesChronological(tracksA, tracksB)` / `mergeRoutesSimple(tracksA, tracksB)` の3関数として実装（要件定義書 6.5）。いずれも `Track[]` を受け取り新しい `Track[]` を返す純粋関数。

**トラックを統合して結合**（`mergeRoutesUnified`）:
1. 両ルートの全 Track.points を 1 つの配列にマージ
2. `time` でソート → 1 本の Track に結合
3. `tracksB` に空配列を渡すことで、1 ルート内の複数トラックを 1 本に統合する用途にも使う（`EditModePanel.tsx` の「ルートを1つだけ選択」フロー）

**トラックを時系列で結合**（`mergeRoutesChronological`）:
1. ルート A の Track 配列 + ルート B の Track 配列を連結
2. 各 Track の開始時刻でソート（Track 単位は保持）

**トラックの単純接続**（`mergeRoutesSimple`）:
1. ルート A の tracks と ルート B の tracks を単純連結（時刻不要）

結合先は `mergeTargetIds`（5.2）で選択された2ルート。確定後、ルート A に統合結果を適用し、ルート B は `removeRoute()` で削除する。

**時刻データの必須検証**（要件定義書6.5）: 「トラックを統合(`unified`)」「時系列(`chronological`)」は時系列ソートを行うため全ポイントに `time` が必要。`EditModePanel.tsx` の `handleMerge` は結合実行前に対象ルートの全ポイントが `time` を持つか検証し、欠落があればエラートーストで中止する（「単純接続」を案内）。「単純接続(`simple`)」は時刻不要。

### 14.4 間引きアルゴリズム（routeEditors.ts）

```
cumDist = 0
result = [points[0]]
for i in 1..N-1:
  cumDist += haversineM(points[i-1], points[i])
  if cumDist >= interval OR points[i].waypoint OR i == N-1:
    result.push(points[i])
    cumDist = 0
```

### 14.5 部分編集アルゴリズム（routeEditors.ts）

要件定義書 6.2 に対応。

- `extractPartialEditRange(points, centerIndex)`: クリックしたインデックスを中心に前後 300 点（最大 601 点）を切り出し `{ startIndex, points }` を返す。トラック総点数が 601 以下なら全体を対象にする。
- `nearestSegmentInsertIndex(points, lat, lng)`: 各セグメントの中点とクリック地点との距離を比較し、最も近いセグメントの直後を挿入位置として返す（青ライン上クリックでのポイント追加に使用）。
- `interpolatePointTime(prev, next, newPoint)`: 前後ポイント間の距離に対する新規ポイントの位置比で時刻を線形補間する。
- 確定時（`EditModePanel.tsx` の `handlePartialEditConfirm`）は `Array.prototype.splice(startIndex, originalLength, ...points)` で元トラックの該当区間を作業コピーに置換する。

### 14.6 重複ポイント除去（routeEditors.ts）

要件定義書 4.2 に対応。`dedupeConsecutivePoints(points)`: 隣接する2点の緯度・経度・時刻がすべて一致する場合、後続の点を除去する。ファイル読込み後（`useFileLoader.ts`）に全トラックへ適用し、除去件数をトースト通知する。

### 14.7 時間シフト・区間再配分（routeEditors.ts）

要件定義書 6.7 に対応。

- `shiftTime(points, newDateStr?, newTimeStr?)`: 先頭ポイントの日付・時・分のみを指定値に変更した際の差分（デルタ）を全ポイントの時刻に加算する。秒は変更対象外のため自動的に元の値を維持する。
- `redistributeTimeWithRange(points, startTime, endTime)`: `redistributeTime`（14.2）による配分後、全セグメントのオフセットを合計時間が `endTime - startTime` に一致するようスケーリングする（一括再計算モードの終了時刻指定、およびルート作成モードの開始/終了日時指定の両方で使用）。

### 14.8 トラック名書式（routeEditors.ts）

要件定義書 6.8 の複数行テキストボックス編集に対応。`trackToNameLine(track)` / `parseTrackNameLine(line)` で `<name>名前<number>番号` 形式の文字列とトラックの `name` / `number` フィールドを相互変換する（名前・番号ともブランク可）。

## 16. 非機能設計

### 16.1 レスポンシブ対応

| ブレークポイント | 変更内容 |
|---------------|---------|
| `< 768px`（モバイル） | 右サイドバーはヘッダーのボタンで、画面の下からのシートとして開く（2026-11-19 から。以前は非表示）、ツールバーを折り畳み、タイムライン縦表示に変更 |
| `768px 〜 1024px`（タブレット） | 右サイドバーを折り畳み（手動展開可） |
| `>= 1024px`（PC） | 全要素を表示（右側のパネル・下側のタイムラインは、それぞれ折りたためる。2026-11-19 から） |

**実装（2026-07-02）**: `hooks/useBreakpoint.ts` が `window.matchMedia` で上表のブレークポイントを判定し、`'mobile' | 'tablet' | 'desktop'` を返す。CSSのメディアクエリだけでは表現しづらい構造的な分岐（サイドバーを描画するかしないか、タイムラインの仮想化方向）を、このフックによるJS分岐で実現している。

- **右サイドバー**: PCでは `AppLayout.tsx` が `RightSidebar` を常時描画する。タブレットでは `uiStore.sidebarOpen` が `true` のときのみ、地図の上に絶対配置の半透明背景＋サイドバー本体を重ねて表示する（`AppHeader.tsx` の `PanelRightOpen`/`PanelRightClose` ボタンで `toggleSidebar()` を呼ぶ）。モバイルでは `RightSidebar` 自体を描画せず、アクセス手段を提供しない（表の記述通り「非表示」を文字通り実装し、タブレットの「手動展開可」とは区別した）。
- **ツールバー折り畳み**: `EditToolbar.tsx` はモバイル幅のとき、現在の編集モードのアイコン・ラベルのみの1行表示＋「編集モード」トグルボタンに切り替わり、タップすると全モードのグリッドメニューが展開する。タブレット・PCでは従来通り横スクロール可能な1行のボタン列。
- **タイムライン縦表示**: `VirtualTimeline.tsx` は `useBreakpoint()==='mobile'` のとき `@tanstack/react-virtual` の `horizontal` オプションを `false` にし、縦スクロールの仮想リストに切り替える。各行は横1列（インデックス・時刻・緯度経度・標高・距離・速度）にまとめたコンパクトなレイアウトで表示する。
- **（2026-11-19 に解消）** リサイズハンドルは `layout/ResizeHandle.tsx` に共通化し、ポインターのイベント（マウス・タッチ・ペン）と矢印キーで動く。以下は当時の記録。**既知の制約**: 下部ペインの高さリサイズハンドル（`AppLayout.tsx`）はマウスドラッグのみに対応しており、タッチドラッグには未対応（モバイル・タブレットでは高さ変更ができない）。要件定義書が想定する「最低限のレスポンシブ対応」の範囲内と判断し、今回は対応を見送った。
- **z-index に関する注意点**: 地図（Leaflet）のラッパー `div` には Tailwind の `isolate`（`isolation: isolate`）を付与している。Leaflet内部の各ペイン（`markerPane` は z-index:600、`popupPane` は700など）が独自のスタッキングコンテキストに閉じ込められないと、タブレットのサイドバーオーバーレイ（z-30/z-40）より上に描画されてしまうバグが実装時に発生したため、`isolate` によってLeafletの高いz-indexを地図コンポーネント内部に閉じ込めている。同様に地図の上に要素を重ねるUIを今後追加する場合はこの制約に注意すること。

### 16.3 パフォーマンス目標

| 項目 | 目標 |
|------|------|
| ファイル読み込み〜地図表示 | 10,000 点のファイルで 1 秒以内 |
| タイムラインスクロール | 60fps を維持 |
| 部分編集マーカー描画（601 個） | 500ms 以内 |

**実測結果（2026-07-02、本番ビルド）**: ファイル読み込み〜地図表示 862ms（達成）、部分編集マーカー描画 602個/150ms（達成）、タイムラインスクロール 約38.7fps（未達）。タイムラインスクロールについては `VirtualTimeline.tsx` のカードを `React.memo` 化し、隣接ポイント間距離を `useMemo` で事前計算し、スクロール位置追跡の `scroll` イベントハンドラを `requestAnimationFrame` で間引く3点の最適化を行った上での数値であり、対策前（同条件下で約24fps）からは改善している。残る乖離は測定方法自体の特性（プログラム的な `scrollLeft` 代入によるベンチマークであり、実際のネイティブスクロールとは負荷特性が異なる）にも起因すると考えられ、詳細は `designs/実装チェックリスト.md` の非機能要件セクションを参照。

**再計測（2026-11-19、本番ビルド、`npm run test:perf`）**: 計り方を、本物のホイールのイベントを送って `requestAnimationFrame` の間隔を集める方式に替えた。タイムラインスクロールは 10,000 点で中央値 59.9 fps・平均 58.0 fps・下位 5 % 59.5 fps（**達成**）。50,000 点は平均約 35 fps（参考）。主な原因は、スクロール中にカードがマウスの下を流れてホバーが起き、ストア全体を購読していた標高グラフ・地図・タイムラインがそのたびに描き直されていたこと（designs/機能追加・UI改善設計書.md E3）。
