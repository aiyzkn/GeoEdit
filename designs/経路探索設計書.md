## 1. 背景と目的

現在の作成モードは、交差点や曲率の変わる地点ごとにクリックして点を置く方式で、長いルートほど時間がかかる。
これを「**通過点（アンカー）を数点置くと、その間を経路探索で自動的に結ぶ。気に入らないところだけ利用者が直す**」方式に改める。

### 1.1 ユーザー要件（2026-11-15）

| # | 要件 |
|---|---|
| R1 | 経路探索で、ある程度自動的にルートを用意する |
| R2 | 編集は Google マイマップのように、途中の地点をドラッグ＆ドロップで動かすと前後の区間も含めて引き直される |
| R3 | 上位の道路を優先する: 高速道路 ＞ 有料道路 ＞ 国道 ＞ 県道 ＞ 市区町村道 ＞ 里道。国道どうしの交差点を県道でショートカットする「抜け道」は通らない |
| R4 | 最終的な線は、地理院地図の地図画像の道路中心に合っていること |

## 2. 経路探索の方式（比較と結論）

### 2.1 結論

**国土地理院ベクトルタイル（`experimental_bvmap`）の道路中心線から、ブラウザ内で道路グラフを組み立てて探索する。** 外部の経路探索 API は使わない。

理由（強い順）:

1. **R3 を仕様どおりに実装できる。** 道路の階級（`rdCtg`・`motorway`・`tollSect`・`rnkWidth`）がタイルに入っており、コスト関数を自前で決められる。公開の経路探索 API は「最短時間」が基本で、階級の厳密な優先（抜け道の禁止）を指定できない
2. **R4 のズレが原理的に小さい。** ベクトルタイルの道路中心線は、地理院地図（標準地図）の画像と同じ電子国土基本図が出どころ（z14〜16 のフィーチャの `orgGILvl` は 2500 = 都市計画図レベル）。OSM の線を地理院地図の画像に合わせ直すより、はじめから同じ測量成果の線を使うほうが、後段のマップマッチングが軽い（または不要）
3. **既存の方針と合う。** マップマッチング設計書 §1 の「外部サービスを使わず、ブラウザ内で完結」、基本設計書 §13.4 の「外部 API キー不要」を保てる。タイルの取得先も、すでに表示に使っている `cyberjapandata.gsi.go.jp` だけ
4. **ドラッグ中の再探索を、通信の往復なしで行える**（タイルを取得済みの範囲なら、探索は手元の計算だけ）

### 2.2 比較

| 観点 | A. OSM 系の公開 API（OSRM / Valhalla など） | **B. 地理院ベクトルタイル + ブラウザ内探索（採用）** | C. 自前のサーバーで経路探索エンジン |
|---|---|---|---|
| 階級の優先（R3） | × 既定は最短時間。OSRM の公開サーバーはプロファイルを変えられない。Valhalla は高速・有料の「使う度合い」までで、抜け道の禁止は表せない | ◎ コスト関数を自前で定義 | ◎ プロファイルを自作できる |
| 地理院地図とのズレ（R4） | × 出どころが別。全線のマップマッチングが必須 | ○ 同じ出どころ（ズレの大きさは §9 で実測する） | × OSM なら A と同じ |
| 一方通行・右左折の規制 | ◎ ある | × **属性が無い**（§8-1） | ◎ |
| 長距離（数百 km） | ◎ 速い | △ タイルの量が増える。2 段階の探索で抑える（§4.5） | ◎ |
| 運用 | 公開サーバーは利用の節度が前提で、止まる・制限されることがある。商用の API はキーが要る | 静的サイトのまま。タイルは「提供実験」で、仕様変更・終了がありうる | サーバーの運用と費用が要る。静的サイト（Cloudflare Pages）の前提が崩れる |
| ライセンス | 出力したルートに ODbL の帰属が及ぶ | 地理院タイルの利用規約（出典の明示）。表示ですでに従っている | エンジンとデータによる |

A の API についての記述（OSRM の公開サーバーの制約、Valhalla の指定できる項目）は、このセッションでは実物で確かめていない（一般に知られた仕様に基づく）。採用しないので、追加の確認はしない。

### 2.3 このセッションで実タイルから確かめた事実（2026-11-15。日本橋付近 経度 139.774・緯度 35.684 を含むタイル）

| ズーム | `road` レイヤーのフィーチャ数 | 入っている `rdCtg` | 備考 |
|---|---|---|---|
| z16（40 KB） | 490（すべて線） | 0・1・2・3 | `ftCode` 22xx・24xx（道路縁などと推測）も混ざる。中心線は 27xx |
| z14（579 KB） | 3,993 | 0・1・2・3 | `ftCode` は 27xx だけ。全階級がそろう。`orgGILvl` = 2500 |
| z12（55 KB） | 757 | 0・1・3 だけ | 市区町村道（2）が無い。`orgGILvl` が無い（出どころが別と推測） |
| z9（231 KB） | 4,862 | 0・3 だけ | 国道と高速だけ |

- 属性: `rdCtg`（0 / 1 / 2 / 3）、`motorway`（0 / 1 / 9）、`tollSect`（0 / 1。z12 以下は 9 もある）、`rnkWidth`（0〜4）、`lvOrder`（0〜3）、`medSect`（0 / 1）、`ftCode`、`Width`（一部だけ）
- z16 のタイルで `rdCtg = 3` の数（46）・`motorway = 1` の数（46）・`tollSect = 1` の数（46）が一致した
- **一方通行・右左折の規制・制限速度にあたる属性は無い**
- 線の端点が同じ座標に集まる数: z14 で 3 本が 1,286 か所、4 本が 579 か所。線は交差点で切れており、**端点の一致でつながりを復元できる見込み**（タイルの境界をまたぐ接続は未確認。§9）
- **ズームが下がるほど下位の道が落ちる**（z9 = 国道・高速、z12 = + 県道、z14 以上 = 全部）。R3 の階級と対応しており、長距離の粗い探索に使える（§4.5）

確かめていないこと（推測）: 各コードの意味。`rdCtg` は 0 = 国道、1 = 都道府県道、2 = 市区町村道等、3 = 高速自動車国道等と読んでいる（数の一致と、z9 に 0 と 3 だけが残ることからの推定。地理院の仕様書で確認する。§9）。

## 3. 用語とデータモデル

| 用語 | 意味 |
|---|---|
| アンカー | 利用者が置いた通過点（始点・経由点・終点）。地図上のマーカー |
| 区間（leg） | 隣り合う 2 つのアンカーの間。経路探索の単位 |
| 区間の線 | 区間の実際の点列。確定時にルートの点になる |

```ts
// src/types/editor.ts に追加
type LegMode = 'auto' | 'straight'          // 経路探索 / 直線（手動）

interface CreateAnchor {
  id: string
  lat: number; lng: number                  // 利用者が置いた位置（道路へ寄せた後の位置）
  legMode: LegMode                          // 「ひとつ前のアンカーからこのアンカーまで」の結び方。先頭では使わない
}

interface CreateLeg {
  fromId: string; toId: string
  status: 'pending' | 'ok' | 'fallback'     // 探索中 / 成功 / 探索できず直線で代用
  points: { lat: number; lng: number }[]    // 両端を含む
  distance: number                          // m
}
```

- `editorStore` の `createPoints: {lat,lng}[]` を `createAnchors: CreateAnchor[]` と `createLegs: CreateLeg[]` に置き換える。**確定時の点列 = 各区間の `points` の連結**（つなぎ目の重複を除く）
- 既存のルートへの適用（区間の引き直し・追記）は、この状態に「確定したときの行き先」（`DraftTarget`）と、動かせないアンカー（`locked`）を足して実現する。[機能追加・UI改善設計書](機能追加・UI改善設計書.md) の B0〜B2
- すべての区間が `straight` のとき、動きは現在の作成モードと同じになる（後方互換。既存の E2E `create-route.spec.ts` を通す基準）

## 4. 経路探索の設計

### 4.1 モジュール構成

```
src/lib/routing/
├── index.ts          # 公開 API: routeLeg()
├── types.ts          # RoadClass / GraphNode / GraphEdge / RouteResult
├── roadTiles.ts      # ベクトルタイルの取得・デコード・LRU キャッシュ（road レイヤーだけを残す）
├── roadClass.ts      # タイルの属性 → RoadClass の対応（§4.3）
├── graph.ts          # タイル → グラフ（端点の一致でノードをまとめる。タイル境界の縫い合わせ）
├── snap.ts           # アンカー → 最寄りの辺への垂線の足（仮のノードを入れる）
├── search.ts         # 階級つきの最短経路探索（純粋関数。§4.4）
└── corridor.ts       # 長距離の 2 段階探索（§4.5）
```

- `graph.ts`・`search.ts`・`roadClass.ts`・`snap.ts` は、Leaflet・DOM・fetch に依存しない純粋関数にする（`node --test` で単体テストする。`mapMatch/` と同じ決まりで、ディレクトリ内は `@/` エイリアスを使わない）
- タイルのデコードは `@mapbox/vector-tile` + `pbf`（`maplibre-gl` が内部で使っているものと同じ。直接の依存として足す）
- 探索は重いので **Web Worker** で動かす（Vite の `new Worker(new URL(...), { type: 'module' })`）。メインスレッドは結果を受け取って描くだけ

```ts
// src/lib/routing/index.ts
export async function routeLeg(params: {
  from: { lat: number; lng: number }
  to: { lat: number; lng: number }
  options: RoutingOptions            // 使う階級の上限など（§4.6）
  signal?: AbortSignal               // ドラッグ中の古い探索を止める
}): Promise<RouteResult>             // { status: 'ok' | 'fallback', points, distance, reason? }
```

失敗（タイルを取れない・道がつながらない・時間切れ）のときは throw せず、`status: 'fallback'` で 2 点を直線で結んだ結果を返す（`matchPoint()` と同じ「黙って代替する」方針。ただし利用者には区間の見た目とトーストで知らせる。§5.5）。

### 4.2 グラフの組み立て

1. 対象のタイル（既定は **z14**。全階級がそろう最小のズーム）を取得し、`road` レイヤーのうち中心線（`ftCode` が 27xx）だけを残す
2. タイル内の座標（extent 4096）を、世界座標（z14 のピクセル × 4096 の整数格子）に直す。**整数のまま**ノードのキーにする（浮動小数の比較をしない）
3. 線の両端をノードにする。同じキーの端点を 1 つのノードにまとめる。線の途中の点は、辺の形として持つだけ（ノードにしない）
4. タイルの境界で切られた線は、境界上の端点が隣のタイルの端点と同じキーになる前提で、そのままつながる。一致しないとき（丸めの差）は、境界上に限って許容差 1〜2 格子で寄せる（§9 で実物を確かめて決める）
5. 立体交差: 線が交わっていても端点を共有していなければ、つながない（中心線のデータは平面交差で切れているはず、という前提。`lvOrder` が違う辺どうしを境界の寄せでつながないようにする）
6. 辺には 長さ（m）・階級（§4.3）・形（点列）を持たせる。**辺は双方向**（一方通行の属性が無いため。§8-1）

### 4.3 道路の階級（`RoadClass`）

要件の 6 階級を、タイルの属性から決める。上から順に当てはめる。

| 階級 | 値 | 判定（案。§9 で仕様書と実物を照らして確定） |
|---|---|---|
| 高速道路 | 6 | `motorway = 1` または `rdCtg = 3` |
| 有料道路 | 5 | 上に当てはまらず `tollSect = 1` |
| 国道 | 4 | `rdCtg = 0` |
| 県道（都道府県道） | 3 | `rdCtg = 1` |
| 市区町村道 | 2 | `rdCtg = 2` で、下の「里道」に当てはまらない |
| 里道 | 1 | `rdCtg = 2` 以外のその他・不明、または幅員の区分が最小（`rnkWidth` の 3 m 未満にあたる値）、または徒歩道・庭園路の `ftCode` |

- 対応は `roadClass.ts` の 1 つの表にまとめる（コードの意味が推測と違っていたときに、直す場所を 1 か所にする）
- 判定できない辺は「里道」にする（知らない道を優先しない）

### 4.4 探索のアルゴリズム（R3 の実現）

「上位の道を優先」と「抜け道を通らない」は別のことなので、2 つの仕組みで表す。

**(1) 階級ごとの重み** — 辺のコスト = 長さ × 重み。上位の道ほど軽い。

| 階級 | 高速 | 有料 | 国道 | 県道 | 市区町村道 | 里道 |
|---|---|---|---|---|---|---|
| 重み（初期値） | 1.0 | 1.2 | 1.6 | 2.4 | 4.0 | 8.0 |

**(2) 山型の制約（谷の罰則）** — 経路の階級の並びは「**登って、いちばん上を走って、降りる**」山型を原則にする。いったん階級を下げたあと、また上げること（谷）に、大きな罰則を足す。

- 探索の状態を（ノード, 相）にする。相は「登り」（まだ階級を下げていない）と「降り」（一度でも下げた）の 2 つ
- 「登り」の相: 同じか上の階級の辺へは、そのまま進める。下の階級の辺へ進むと、相が「降り」に変わる（罰則なし。目的地へ降りるのに必要）
- 「降り」の相: 同じか下の階級の辺へは、そのまま進める。**上の階級の辺へ戻るときに罰則**（初期値: 階級の差 1 つにつき 2,000 m 相当）を足す。相は「降り」のまま
- 国道 → 県道 → 国道 のショートカットは「降りてから登る」なので、罰則がかかる。県道で縮まる距離が罰則より小さいかぎり、国道どうしの交差点を通る（R3）
- 罰則を無限大（禁止）にしない理由: 実物の道路網には、国道と国道の間を短い市道の連絡路がつなぐ交差点や、上位の道が途切れている区間がある。禁止にすると経路が見つからなくなる。罰則なら、ほかに道が無いときだけ谷を通る
- 例外: 始点・終点の近く（初期値 300 m 以内）の谷には罰則をかけない。アンカーを細い道の先に置いたとき、最寄りの大きい道へ出るまでの上り下りを自然にするため

状態の数は 2 倍になるだけで、ダイクストラ法（優先度つきキュー）のまま解ける。距離の下限（直線距離 × 最小の重み 1.0）を使う A* にする。

重み・罰則・例外の半径は `search.ts` の定数の表にまとめ、§9 の検証ルートで調整する。

**アンカーを区間ごとに分けて探索する点に注意**: 山型の制約は区間ごとにかかる。利用者が県道の上に経由点を置けば、その前後は「降りる → 登る」が罰則なしで通る（経由点は「ここを通れ」という指示なので、これが望む動き）。

### 4.5 長距離の区間（2 段階の探索）

z14 のタイルは市街地で 1 枚 500 KB を超える（日本橋で 579 KB。約 2 km 四方）。始点と終点を囲む四角形のタイルを全部取ると、長い区間では量が大きすぎる。

- **短い区間**（直線距離が初期値 8 km 以下）: 2 点を結ぶ線分のまわり（幅は距離に応じて広げる）の z14 のタイルを取り、そのまま探索する
- **長い区間**: 2 段階にする
  1. 粗い探索: z12（国道・県道・高速だけ。1 枚が約 10 km 四方で軽い）でグラフを作り、経路の見当をつける。さらに長い区間（初期値 150 km 超）は z9（国道・高速だけ）を使う。始点・終点から粗いグラフへの出入りは、両端のまわりの z14 のタイルで探索してつなぐ
  2. 細かい探索: 粗い経路に沿った帯（回廊）の z14 のタイルだけを取り、帯の中で §4.4 の探索をやり直す。**最終の線は必ず z14 の中心線から作る**（z12 以下の線は出どころが別と見られ、地図画像とずれるおそれがあるため、見当をつけるためだけに使う）
- 道がつながらない・帯の中に経路が無いときは、帯を広げて 1 回だけやり直し、それでも無ければ `fallback`
- タイルは LRU でキャッシュする（デコード後の `road` の線だけを持つ。建物などは捨てる）。同時に取得する数は 6 まで

ドラッグの編集で引き直す区間はたいてい短いので、ふだんの操作は 1 段階で済む。

### 4.6 探索のオプション

| 項目 | 既定 | 内容 |
|---|---|---|
| 使う階級の上限 | 高速道路まで | 「有料道路を使わない」「高速道路を使わない」を選べる（自転車・徒歩のルートを作る人のため）。除いた階級の辺はグラフに入れない |

利用者の要件には無かった項目（提案）で、入れると決まった（§10.2 の Q3）。入れても R3 の順は変わらない。

## 5. 編集 UI の設計（R2）

### 5.1 操作の一覧

| 操作 | 動き |
|---|---|
| 地図をクリック | 末尾にアンカーを足す。直前のアンカーからの区間を経路探索で結ぶ |
| **Ctrl（macOS は Cmd）+ クリック** | 末尾にアンカーを足し、その区間を**直線**で結ぶ（道の無いところ・探索の結果が合わないところ用。いまの「Ctrl でマップマッチングを飛ばす」と同じ「Ctrl = 自動の補正をしない」の意味にそろえる） |
| アンカーをドラッグ | 前後の 2 区間を引き直す |
| **区間の線の上をドラッグ** | つかんだ位置に経由点（アンカー）を差し込み、その区間を 2 つに分けて引き直す（Google マイマップと同じ） |
| アンカーをクリック | そのアンカーを消す。前後の 2 区間を 1 つにまとめて引き直す |
| Ctrl+Z / Ctrl+Y | 直前の操作（追加・移動・差し込み・削除）を取り消す / やり直す |
| 「確定」 | 全区間の線を連結してルートにする。標高の自動取得は、いまと同じ |

- 作成モードのパネルに「**経路探索**」のチェックボックスを足す（既定 ON）。OFF のとき、足す区間はすべて直線になり、いまの作成モードと同じ動きになる
- いまの「マップマッチング」のチェックボックスは残す（アンカーを置く位置の補正に使う。§6）

### 5.2 線の上をドラッグして経由点を差し込む

- 区間の線にマウスを乗せると、線の上のいちばん近い位置に「つまみ」（白い小さな丸）を出す。つまみは 1 つだけを使い回す（マウスの位置で動かす）
- つまみをドラッグし始めた時点で、その区間にアンカーを差し込む。あとは「アンカーをドラッグ」と同じ処理
- つまみをクリックしただけ（動かさない）なら、何もしない（誤って経由点が増えないように）
- タッチ端末: 線の長押しでつまみを出す（細かい検証は §9）

### 5.3 ドラッグ中の描き方

- ドラッグ中: 動かしているアンカーの前後を、**仮の直線**（点線）で見せる。あわせて、探索を間引いて走らせ（初期値 150 ms ごと。前の探索は `AbortSignal` で止める）、結果が返ったら仮の線を経路に差し替える。タイルを取得済みなら、ほぼ追従する
- ドロップ時: 位置を確定して、前後の 2 区間を探索する。結果が返るまで、その区間は `pending` の見た目（点線・薄い色）
- 引き直すのは**動かしたアンカーの前後の 2 区間だけ**。ほかの区間は触らない（手で直したところが、離れた場所の操作で変わらないこと）

### 5.4 探索の順序の保証

- 区間ごとに「世代番号」を持ち、返ってきた結果の世代が古ければ捨てる（ドラッグを続けたときに、古い結果で上書きされないように）
- いまのクリックの順序を保つ仕組み（マップマッチング設計書 §5.2 のキュー）は、アンカーの追加の順に引き続き使う。区間の探索はキューに入れず、並行で走らせる（1 つの区間が遅くても、次のクリックを待たせない）

### 5.5 見た目とフィードバック

| 状態 | 線 |
|---|---|
| 経路探索で結んだ区間（`ok`・`auto`） | 実線・青 |
| 直線で結んだ区間（`straight`） | 点線・青（いまの作成中の線と同じ） |
| 探索中（`pending`） | 点線・薄い青 |
| 探索できず直線で代用（`fallback`） | 点線・橙。トーストで 1 回だけ知らせる（「経路が見つからないため直線で結びました」） |

- アンカーのマーカーは、いまの丸（末尾だけ大きい）を使う。経路の途中の点（区間の線の頂点）にはマーカーを出さない
- パネルに、合計の距離を出す

### 5.6 取り消し・やり直し

いまの `createRedoPoints`（末尾の 1 点を退避するだけ）では、移動・差し込みを戻せない。作成中の状態（`createAnchors` と `createLegs`）の**スナップショットの履歴**に替える（操作の確定ごとに 1 つ。ドラッグ中の途中経過は積まない。上限 100）。戻したときは区間の線も一緒に戻るので、探索をやり直さない。

## 6. 地図画像とのズレと、マップマッチング（R4）

方式 B では、線の出どころが地図画像と同じなので、**全線のマップマッチングは、ズレを実測してから要否を決める**（§9-3）。

| 段 | いつ | 何をするか |
|---|---|---|
| アンカーの補正 | アンカーを置いた・動かしたとき | 経路探索が ON の区間では、アンカーを**グラフの最寄りの辺**へ寄せる（`snap.ts`。初期値 30 m 以内。届かなければ、置いた位置のまま、最寄りの辺まで直線で結ぶ）。経路探索が OFF（直線）のときは、いまの画像によるマップマッチング（`matchPoint()`）を使う |
| 線の補正（条件つき） | 区間の探索のあと | §9-3 の実測で、中心線と画像の道路中心のズレが許容（初期値: z16 で 2 px = 約 2 m）を超える場面があるときだけ入れる。区間の線の頂点と、頂点の間を一定の間隔で取った点を、いまの `analyzePatch()` で道路の中心へ寄せる。寄せる量は小さい範囲（パッチの半径以内）に限り、隣の点と向きが逆の補正は捨てる（注記・交差点での誤りを防ぐ） |

- 線の補正を入れる場合も、対象は地理院の画像のレイヤー（標準・淡色）を表示しているかどうかに関係なく、**標準地図のタイルを裏で取得して**行う（線を合わせる先は地理院地図の画像、と要件にあるため）。利用者の決定は §10.2 の Q2
- ズレが小さければ、線の補正は実装しない（タイルの取得と計算を増やさない）

## 8. 制限事項・既知のリスク

1. **一方通行・右左折の規制・時間帯の規制を見ない**（タイルに属性が無い）。車が実際には走れない向きの経路が出ることがある。利用者がドラッグで直す前提。GPX のルートを「描く」道具であって、カーナビではない、と割り切る
2. **ベクトルタイルは「提供実験」**。属性・レイヤーの名前が変わる、提供が終わる、がありうる。属性の読み取りを `roadClass.ts`・`roadTiles.ts` に閉じ込め、取れないときは `fallback`（直線）で作成モードそのものは使えるようにする
3. **分離帯のある道路**: 上下線が別の中心線になっているか、1 本かは場所による。別の線のとき、向きを見ないので反対車線の側を通ることがある（見た目の差は数 m）
4. **立体交差・側道**: §4.2-5 の前提（平面交差で切れている）が外れる場所では、つながるはずの道がつながらない・つながらないはずの道がつながる
5. **道路の階級と、実際の走りやすさは同じではない**。重み（§4.4）は距離にかけるだけで、所要時間は見ない
6. **海外・地理院のタイルが無い範囲**では探索できない（直線で代用）
7. 市街地の長い区間では、タイルの取得に数秒〜十数秒かかることがある（進み具合を表示する）
8. フェリーの航路は `road` に入っていない（別レイヤー）。海をまたぐ区間は直線で結ぶ

### 9.2 試験

- 単体（`node --test`）: 小さな手作りのグラフで、(a) 国道 2 本が交差し、その角を県道が斜めに結ぶ → 県道を通らない、(b) 国道が途切れ、県道でしかつながらない → 県道を通る（谷の罰則を払う）、(c) 始点が市道の奥 → 最寄りの上位の道へ出る、(d) 高速を除く設定 → 高速を通らない、(e) つながらない → `fallback`。タイル → グラフ（端点のまとめ・境界の縫い合わせ）は、保存した実タイルの断片で
